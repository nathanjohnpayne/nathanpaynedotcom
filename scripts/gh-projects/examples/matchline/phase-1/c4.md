Second step of the core loop: pasted JD in, structured `JobRequirementUnit[]` out. Cheaper than extraction because JDs are shorter and more structured than resumes, but critical — if the Requirements are wrong, the matches are wrong.

**Blocks on:** #__C1_NUM__ (owner_uid wiring — Requirements carry `owner_uid` too for query-scoping parity).

**Scope:**

1. **Functions endpoint.** `functions/src/parsing/index.ts` exposes `parseJobDescription(roleId, text)` as a callable. Uses `modelFor("requirement_parsing")` (Haiku per PRD — cheaper, this stage doesn't need frontier).
2. **Prompt.** `functions/src/prompts/job-requirement-parsing.md`. Extract each discrete requirement with `priority` (`high`/`medium`/`low`), `must_have` (boolean), `category` (skill/tool/domain/experience_level/scope/soft_skill/credential), `extracted_from` (which JD section), and the raw phrase.
3. **Normalization.** Canonical vocabularies live in the ontology seed (#__C5_NUM__). This ticket can ship a pass-through `normalized_requirement = raw_text.trim().toLowerCase()` and be tightened by the ontology ticket.
4. **Embeddings.** `embedMany` over every `normalized_requirement`, cached on the Requirement doc.
5. **Write path.** Requirements stored under `jobRequirementUnits` keyed by role_id + unique id; service layer in `src/services/roles.ts` already has the list function, extend with `upsertRequirement`.
6. **Role Detail → Requirements tab.** Thin UI — list + edit each parsed Requirement. Editing re-runs the embedding on save.

**Non-goals:**
- JD scraping from URLs. PRD is explicit: paste-only in V1.
- Signals beyond what's in the schema (seniority, scope extraction is ok; everything else waits).

**Verification:**
- Given a fixture JD, the parser produces Requirements with fields populated; ≥ 80% of `must_have`/`priority` annotations match a manual reference on a 10-JD fixture set.
- Parse time p95 ≤ 4 s per spec § Execution targets.
