The UI surface for the scoring engine. This is where most per-role time is spent and where approvals for generation come from.

**Blocks on:** #__C1_NUM__ (matching engine produces UnitMatches to display).

**Scope** (`src/routes/RoleDetail.tsx` replaces the Sprint 0 placeholder):

1. **Tab scaffold.** Three tabs: Requirements, Matches, Applications. This ticket ships Matches; Requirements tab ships as part of #__PARENT_NUM__'s JD parsing sub-issue (basic) and gets fleshed out here.

2. **Matches tab — side-by-side view.** Rows are Requirements. For each Requirement, the top-K (3? 5?) UnitMatches, sorted by `final_score` descending. Each match card shows:
   - The Requirement phrase.
   - The matched Unit's `normalized_summary`.
   - The `final_score` as a 0–100 number with a sub-score breakdown on hover (semantic, skill, domain, tool, seniority, scope, recency).
   - The `rationale` string.
   - The `surface_evidence` — the specific claim being matched.
   - Approve / Reject buttons → `UnitMatch.approved_for_use` toggle.

3. **Gaps view.** Separate pane or filter. Surfaces Requirements with `must_have: true` where no match clears a threshold (say `final_score < 0.4`). Honest: if Nathan has no Experience Unit for a hard requirement, the Matches tab says so.

4. **Hydration.** Service layer fetches matches via `listMatchesForRequirement` for each Requirement. On first render with no matches yet, trigger generation (call matching engine).

5. **Performance.** Matches should feel instant once embeddings exist. Cache aggressively; recompute only when a Unit or Requirement changes.
