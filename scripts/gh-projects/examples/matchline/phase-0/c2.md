**P1 review finding on PR #4.**

`firestore.rules` requires every document to carry `owner_uid == request.auth.uid` for reads. Firestore's rule engine evaluates list queries against the query constraint, not just the returned documents, so every `list*` service function must include `where("owner_uid", "==", userId)` or the query will be rejected wholesale. Sprint 0 has no live reads so nothing crashes today, but Phase 1 will trip over this the moment auth lands.

**Scope:**
- Add a shared `ownerScope(userId): QueryConstraint[]` helper (probably in `src/services/firestore.ts` or an adjacent `src/services/auth.ts`). Returns `[where("owner_uid", "==", userId)]`, or `[]` with a clear invariant comment while auth isn't wired.
- Thread the helper into every `list*` function in `src/services/`. The call site changes look like `query(col(), ...ownerScope(userId), ...otherConstraints)`.
- Add a short comment at the top of `firestore.rules` pointing at the helper and the Phase 1 auth ticket so the two sides stay linked.

**Alternative considered and rejected:** inline comments on each list function. Code comments drift faster than a helper; centralizing the seam keeps the rules and the queries from disagreeing silently.

**Verification:**
- `npm run typecheck` passes.
- Grep confirms every `getDocs(query(col()...))` call goes through `ownerScope`.
