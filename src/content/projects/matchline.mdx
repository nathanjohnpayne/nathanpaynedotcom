## The problem, and the evidence behind it

Matchline is built on two premises about the 2026 job market. First, anyone can generate a tailored résumé and cover letter in seconds, so every application is polished and polish is no longer a signal. Second, what remains as signal is specificity a candidate can defend—and a generative writer can't supply it, because the model doesn't know which projects mattered, which numbers are honest, or which claims survive an interview.

**That premise has one piece of evidence behind it, and it is worth being precise about its size.** There is no user research in this project, no interviews, no competitive scan, no market sizing. What exists is a single job search—mine—and its fingerprints are on the design rather than in a document. The evaluation corpus is built from job descriptions on my own prospect list, because the repository notes that those are the most accurate signal available for scoring match quality. The phase milestones are written in the first person: use the product for one real application, then ten. The premise is a hypothesis drawn from one person's experience, and nothing here has tested it against anyone else's.

The one place the reasoning is argued rather than assumed is in the validator, which carries a list of thirteen phrases it refuses to let through—*collaborated cross-functionally*, *drove results*, *moved the needle*—each with a written justification. They survive traceability, because the user did collaborate on something somewhere, and they tell a reader nothing. That is the thesis in its most testable form: the problem is not that applications contain lies, it is that they contain sentences which are true and empty.

So Matchline inverts the usual order. Instead of generating a document from a résumé and a job description, it treats work history as a structured graph of capabilities, outcomes, and evidence, and uses AI to assemble that evidence against a specific opportunity. The model's job is selection, sequencing, and framing. A claim that doesn't trace to something the user has documented and approved is treated as a defect, and the product's central mechanism exists to catch it.

## What is built, what is designed, and what never happened

The project is paused before launch with no public release and no user other than its author. That makes the distinction between designed and implemented behavior the most important thing this page can be clear about, so it is a table rather than a paragraph.

| Capability | State | What backs it |
|---|---|---|
| Résumé pasted into Experience Units | **Implemented** | Full path from the onboarding textarea through an extraction callable to Firestore. Each Unit carries skills, tools, domains, metrics, and a confidence score as required fields, enforced by a strict schema at the extraction boundary. |
| LinkedIn HTML and long-form prose as inputs | **Deferred** | Both exist as provenance values you can relabel an existing Unit with. Neither has an ingestion path; the code says the paste flows are deferred and the pipeline is text-only at V1. |
| Every extracted Unit lands unapproved | **Implemented** | The extraction stamp sets approval false server-side, and the model is barred from returning the field at all. Units authored by hand are the exception—they arrive pre-approved and marked as user-confirmed, because a Unit the user typed is already the user's own assertion. |
| Approved evidence is the only input to matching | **Implemented** | The filter is server-side and duplicated across the matching, generation, and validation pipelines. It is a read gate, not a write gate: no security rule constrains the approval field, so the approval itself is a client write that application code, not the database, keeps honest. |
| Job description parsed into Requirement Units | **Implemented** | Deterministic parsing with light model classification, scored against hand-labeled fixtures. |
| Explainable match scores with surfaced gaps | **Implemented** | Scoring across semantic similarity, skill and tool and domain overlap, seniority, scope, and recency, with unmatched requirements shown in place rather than hidden behind a tab. |

## What the measurements actually said

The quality bar was two numbers: 80% extraction accuracy and 80% match accuracy. Neither was reached, and the distance is the most useful thing this project produced.

The first live evaluation run reported **3.3% extraction accuracy**, which was not a product result—it was a broken metric. The scorer compared generated summaries to hand-labeled ones with string equality, and language models paraphrase, so the number collapsed to nearly zero. Switching to token overlap lifted it to 34%. Switching again, to a coefficient that gives full credit when the labeled set is covered by a longer generated one, lifted it to **50.3%**. Expanding the matching vocabulary from roughly 220 entries to roughly 415 moved extraction one further point, to **51.3%**, and match accuracy from 4.2% to **16.7%**.

Read the sequence carefully: the metric was redefined three times and the system barely moved. Most of the apparent progress was the ruler being fixed, not the product improving—which is the honest reading and the uncomfortable one, and it is why the last working sessions went into measurement rather than features.

Then match accuracy stopped being legible at all. Three samples of one fixture spread from 12.5% to 25.0% and averaged 18.1%: about eight to thirteen points of pure noise, against a target improvement smaller than that. Averaging it away costs money, and money was the binding constraint—a single four-cell run at three samples cost $2.06 against a $25 monthly cap, roughly twelve runs a month, and running the full corpus daily would have cost about forty-five times the combined budget.

That is the state the project is paused in. The last recorded extraction accuracy is **51.3%**, in April; the last recorded match accuracy is **18.1%**, in June; the bar for both is 80%. The continuous-integration gate that would enforce those numbers is still advisory rather than blocking, and the corpus it would enforce against is incomplete—ten résumés and eleven job descriptions, of which only four pairs are hand-labeled with expected matches.

## The artifact

The clearest single thing to look at is not a screenshot of the product. It is the fixture whose only job is to break it.

The zero-fabrication constraint is easy to state and easy to fake: any validator that returns "looks fine" scores well on honest inputs. So the repository carries a hand-labeled adversarial case—a fabricated paragraph attached to a real résumé, claiming a multi-year x86 and Arm CPU roadmap, a hundred-million-VM fleet, a 40% throughput gain on SAP HANA, and $400M in contracts displacing a competitor in two Fortune-50 accounts. None of it traces to any Experience Unit. The fixture enumerates all four untraceable claims with the reason each one fails, records the expected validation status as failed, and states its own purpose in the file: without it, the accuracy metrics could trend upward while the system still leaked fabrications.

It runs in continuous integration against the Firestore emulator, and a passing run means the export was blocked. That is a real proof of the orchestration and a limited one: the language-model checks inside it are mocked in that test, because its integration boundary is the database rather than the model API. So the plumbing provably refuses to ship an untraceable claim. Whether the detector reliably notices one in the wild is the question a user would answer, and no user has.

## How it was built, and where it stopped

Two things about the build are worth a reader's attention: how the work was distributed, and how it ended.

**Agents did the typing and a second agent identity did the reviewing.** As of 2026-08-31, eighty-two commits carry an authoring-agent trailer, sixty-two carry a self-review section, fifty-six reference a priority-graded finding from an external reviewing agent, and forty-five reference a second advisory reviewer. The review was mechanically enforced rather than voluntary: a pre-tool hook blocks pull-request creation when the authoring-agent field or the self-review section is missing.

More to the point, the reviews changed the code. A reviewer caught that the seniority scorer was zeroing every Unit, because extraction emits verbs like *led* and *owned* while the ladder was matching nouns. Another caught a schema converter silently returning an empty object on every model call, which had quietly removed input validation from extraction, parsing, generation, and validation at once. A third caught the matching pipeline discarding a user's rejection on every rerun—my own first reply to that review was wrong, cited a test that did not cover the case, and the reviewer pushed back a second time before it was fixed. One commit records two further findings declined, with reasons. That is the useful evidence: not that review happened, but that it overrode the author.

The caveat belongs on the same page as the claim. The default merge path in this repository is full automation with no human checkpoint. The human wrote the specification, the plan, and the fixture labels, and arbitrates when reviewers disagree—but was not the line-by-line reviewer, and it would be wrong to read the commit count as human oversight.

**The work ended on a date the commits set.** The largest single burst in the repository's history is twelve commits inside sixty-one minutes on 2026-07-06, landing fixes across parsing, matching, validation, and language-model cost, among them a guard for a broken confidence value in the approval-review screen. The Five Across repository is created the next day. Twenty-five days later, on the evening of **2026-07-31** Pacific time, one more product commit lands the eval stage cache. That is the last commit in the repository that touches the application.

Everything after it is automated. As of 2026-08-31, twenty-six commits have landed since that date: dependency bumps from an automated updater, repository-template syncs from [Mergepath](/projects/mergepath/), and a handful of credential and continuous-integration fixes. None of them touch the product. That distinction is the durable one, and it is why this page names the last product commit rather than counting commits since—the automated ones will keep arriving, and any sentence of the form *N commits since* is wrong the week after it is written.

## What would restart it

The repository does not say the project is paused. It does not say why, and it states no condition for resuming, shipping, or abandoning it. What it has is exit criteria for finishing V1, which is a different thing—criteria for building, not for deciding.

So the following are authored here rather than found in the record, and should be read as a commitment made now rather than evidence of one made earlier.

**Resume it when** a single full evaluation run over the completed corpus clears 70% extraction accuracy with match-accuracy noise under five points—the first condition being about the product, the second about whether the number can be trusted at all. The corpus has to be finished first: eleven of its job descriptions are in place and only four pairs are hand-labeled, and labeling is the human work that no agent can do here, because the labels are the ground truth.

**Kill it when** either of two things is true. If the completed corpus shows match accuracy plateauing below 40% after a full tuning cycle on the cheap instruments, the matching approach is wrong rather than untuned, and the honest move is to say so rather than fund another cycle. Or if I finish a job search without reaching for it—the product's own success metric was that it would be the primary tool rather than abandoned for a spreadsheet, and a builder who does not use their own tool under real pressure has answered the question.

**The next evidence needed** is neither of those. It is one real application generated end to end and sent, which is the condition the second build phase set for itself and never met. Until that happens the zero-fabrication constraint remains a design that survives an adversarial fixture and has never met a person in a hurry.

## Status

Paused before launch, with no public release and no user other than the author. Public-release decisions come after V1 has earned its keep on real outcomes, and there are no real outcomes.

There is no usage outcome to report, and the absence is the outcome so far. Whether any application was ever generated or sent is not something the repository records either way—the silence is in the evidence, not a finding of zero. What exists is code across parsing, matching, and validation that was still being fixed into late July 2026, a zero-fabrication design proven against a planted fabrication in continuous integration and never against a user, an evaluation harness whose last recorded numbers are well short of their bar, and an instrument that was finally cheap enough to use on the day the work stopped.

The repository is public. A build is deployed, three months behind that record and behind a sign-in wall, and this page does not link it.
