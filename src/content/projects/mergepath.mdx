## The operator was the review process

Mergepath exists because one person was operating three agent platforms—Claude Code, Codex, Cursor—across a growing fleet of repositories, and the one rule that mattered was being followed only when convenient. Every change goes through a pull request: the rule was in every file the agents read, and all of them could quote it back. One of them would push straight to `main` anyway, usually on a change small enough not to feel like it counted.

Every time, I became the review process—reading diffs after the fact, relaying feedback between sessions, vetting uninspected output by hand. The agents produced more; my confidence did not keep up. That gap is the product problem.

The origin story is told in [Agent Approval Workflow and the Genesis of Mergepath](/blog/agent-approval-workflow-genesis-of-mergepath/). This page is about the decisions that came after the problem had a name, and what each has cost since.

## Six actors, one system

The repository names six roles, and the system owes each something different. The **operator** owns every repository and every setting the automation cannot change, and is where every escalation terminates. The **author identity** is the single account that authors and merges every change, so what landed carries one name. The **authoring agent** declares itself on each pull request—and the repository is careful to call that a declaration rather than proof of who wrote the branch.

Each **reviewer agent** posts under its own machine account and never merges. The **CI service account** holds write access because CI needs it, and is barred from ever holding an approval. And the **human tiebreaker** is a working role rather than an org-chart courtesy, because the escalation triggers are mechanical: a finding re-flagged after a rebuttal, or a round counter past its budget, escalates automatically. Nobody has to decide whether a disagreement is worth raising.

These are the boundaries the system operates inside.

## The decisions

The easy description of Mergepath is an inventory—seven fail-closed CI checks in April 2026, twenty-seven by mid-May, seventy-two as of 2026-08-28, seventy-one of them wired into the lint workflow across eighty invocations—and the inventory is the least useful description, because a count says nothing about judgment. Every mechanism in it exists because a specific failure happened while the fleet was live, and one principle runs under most of them: clearance is bound to the exact commit reviewed, and a content-changing push voids it. What follows are the five decisions a reasonable person could have made differently, and what each cost.

## What the record shows

Adoption and impact are different claims, and this section keeps them apart.

Adoption is real and bounded. The hub has merged 470 pull requests as of 2026-08-28, each through the path it prescribes. The fleet stands at nine repositories—the hub plus eight consumers—and it got there by shrinking: a consumer was archived in August 2026 and retired from the propagation manifest, which is the honest shape of a fleet that retires things. The stress test came in July 2026: 134 review-finding threads across a 24-hour, eleven-PR record, counted as of 2026-08-26 and dissected in [A Perfect Score on the Wrong Axis](/blog/perfect-score-wrong-axis/). And the sharpest single result cuts against the hub rather than for it: seventeen template bugs, catalogued in [`mergepath#75`](https://github.com/nathanjohnpayne/mergepath/issues/75), in code the template's own review had cleared—surfaced downstream, across seven external-review rounds per pull request, once propagation dropped the same files into unfamiliar codebases. Review found the least where the files were most familiar.

The adoption boundary was built to be falsifiable, and it falsifies the flattering reading: the repository has been public and marked as a GitHub template since 2026-03-24 and has zero forks. All eight consumers are my own repositories. The `mergepath` name is reserved on npm and PyPI against squatting; nothing installable has ever been published.

Impact is where the record goes quiet, and that should be said plainly: there is no measure of what the gates save. No savings claim exists anywhere in the repository, and no manual baseline was ever recorded, so there is nothing to subtract from. The two measurement systems that do exist both measure cost—how long external review takes, and the latency budgets the CI suite must stay under. The bootstrap wizard stands up a new repository by performing fifty wrapped operations across four stages, and `--dry-run` performs none of them, printing each one instead; fifty is a count of what is automated, not a measure of time saved, because nobody timed the manual path. What the record supports is three columns—what the gates catch, what they miss, what they cost—and this page stays inside them.

## The premise the fleet does not yet meet

The premise this page used to open with had three clauses: written conventions are not enough, branch protection is mandatory, and review is performed by a different identity than the one that authored the change. The repository measured the middle clause against its own fleet, and it does not hold.

The mechanism is in the repository's architecture decision record on enforcement posture: a GitHub Actions job gates a merge only when branch protection lists it as a required status check. Absent that listing, the job still runs and still goes red—and the pull request merges anyway. On 2026-07-28 the audit found eight of the ten repositories then in the fleet enforcing zero of the five canonical required checks, three of them with no protection on `main` at all, and the hub itself enforcing two of five. That is a dated snapshot, not current state. But the gap it measured is still open: the record is a recommendation awaiting the owner's acceptance rather than a decision anyone has taken—"every repository requires all five" has never itself been settled—and the remediation is deliberately undone, so the weekly audit keeps reporting the drift. Visible rather than silent is a real posture, and a lesser one than closed.

So the honest statement is narrower than the premise: the gates run everywhere and fail closed where they are required, and they are required in fewer places than the standard's own tooling would like. A page that presented this system as infallible automation would be describing a different system.

## What it bought the other projects

Six of the seven projects on this site are consumers of this standard; the seventh is Mergepath itself. What the standard bought them is that their pages get to be about their products: features shipped mid-sailing on Five Across landed as reviewed pull requests, and Override's agent-written engine moved through the same multi-identity review path as everything else in the fleet. Those pages spend a line on governance and the rest on the product. This page is where that line gets audited.

One disclosure belongs at the end, because it is this page's own validation boundary: the pull request that ships it will merge through the system it describes. That proves the choreography runs. It proves nothing else—a system approving its own description is exactly the evidence this standard was built to distrust.
